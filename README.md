# 庙算杯态势感知赛道测评系统（Wargame-Eval）V1.4

可运行的 FastAPI + SQLite 单管理员平台，包含四个正式比赛页面和四个开发者页面，历史报告并入比赛结果页。默认只监听本机；不需要选手编写 Agent。支持从工作区 `images/qa_all.json` 一键导入 **1279 道独立 QA 与 240 个截图帧**，原样保留源文件的题目输入、选项和 GT；仍兼容原始 Markdown ZIP。

V1.4 使用左侧分组导航，正式比赛按 **01 数据集 → 02 参赛名单 → 03 设置并启动 → 04 监控与结果** 操作。顶部显示当前页面标题，不再放置横向步骤导航；正式比赛与开发者选项分别从 01 编号。每队在名单中用下拉框选择唯一参赛版本，支持多文件 JSON 导入、启动前核对冻结名单、批次监控、历史报告、综合 HTML 报告和图表导出。支持队间并行和队内不同套题并发，详见下方“并发与限流”；支持自选跨批次或独立评测记录对比，不改变正式分组排名。批量接口、兼容导入和导出细节见 [批量比赛使用说明](docs/v1.2-competition.md)。

## 参赛分工与 Prompt 提交

**Prompt 由选手设计并提交；推理模式由主办方选择；管理界面由主办方操作。** 选手不需要操作后台或编写 Agent。主办方导入选手原样提交的三段 Prompt、保存版本，统一设置正式批次的推理策略、次数和超时，并冻结配置。正式批次固定全量题库；只有开发者单任务调试可指定题目范围。详细提交要求见 [参赛须知](docs/participant-guide.md)。

选手应将 Prompt 分成三个字段提交，正式导入要求三段均非空，便于主办方安排不同模式的测评：

| 字段 | 由谁设计 | 用途 | 生效时机 |
|---|---|---|---|
| `system` / System Prompt | 选手 | 模型角色、总体原则、信息使用边界与作答约束 | 三种模式均使用；Self-refine 后续轮次继续保留 |
| `initial` / Initial Prompt | 选手 | 首次解题的处理方法和注意事项 | Single-pass 的唯一一次、Self-refine 的首轮、Majority-vote 的每次独立采样 |
| `review` / Review Prompt | 选手 | 要求模型复核、发现错误并修正当前题已有回答 | 仅 Self-refine 的后续轮次；另两种模式不发送 |

三段是同一参赛方案在不同环节使用的指令，不是三道题，也不必三段都发送给每次调用。完整原始题干、背景、选项和截图由平台自动附加，选手不需要粘贴题库或设置题目占位符。GT、参考推理和其他题目的回答不会发送给模型。

主办方决定本轮使用 Single-pass、Self-refine 还是 Majority-vote。同一正式批次的全部队伍使用统一策略、次数、提前结束规则和超时；比较不同策略时应建立不同批次，分别标明条件。调用次数上限和超时由主办方统一设置，实际次数按赛规确认。选手提交的 JSON 不决定本轮使用的策略或调用次数。

## 启动

Python 3.10+，建议使用独立虚拟环境。在项目根目录执行：

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python start.py
```

依赖已安装的环境一条命令启动：

```powershell
python start.py
```

打开 <http://127.0.0.1:8000>，本地 API 路由文档位于 <http://127.0.0.1:8000/docs>，完整 Schema 位于 <http://127.0.0.1:8000/openapi.json>，均不依赖 CDN。端口占用时使用 `python start.py --port 8001`。请只运行一个进程 / 一个 worker，不使用 reload；执行队列归属该进程，SQLite 负责持久化。

可选 Docker：

```powershell
docker compose up --build
```

Docker 绑定主机 127.0.0.1，持久化 `data/` 与 `config/`。Docker 文件已提供，当前交付环境未验证 Docker 构建。

## 主办方正式测评操作

以下流程供**官方测评人员 / 主办方管理员**操作。选手只交付模型服务与 JSON 配置，不进入管理后台。

### 测评前准备

1. 按“启动”一节启动单进程服务，打开 <http://127.0.0.1:8000>。升级或正式比赛前，备份 `data/` 和 `config/`，包括数据库、截图和 `data/.secret.key`，不要将这些私有文件提交到 GitHub。
2. 与选手确认队伍编号、待测方案版本、API 服务窗口、凭据及聚合代理声明。收集符合 [参赛须知](docs/participant-guide.md) 的 JSON，不将密钥粘贴到公开仓库或报告。
3. 向选手公布本轮的统一推理策略、最大调用次数、总超时和提前结束规则。需修改主办方上限时，进入 **开发者选项 → 02 Prompt 与推理 → 主办方执行规则**；当前默认每题最多 3 次请求、共享 120 秒总超时。保存规则本身不调用模型。

### 按四个正式比赛页面执行

| 步骤 / 页面 | 官方人员操作 | 进入下一步前核对 |
|---|---|---|
| **01 数据集** | 四选一：**工作区一键导入**（`qa_all.json` 与截图放在根目录 `images/`）、**手动选择文件**（选 `qa_all.json` 和截图文件夹，浏览器上传）、兼容 ZIP、**本地路径导入**（直接填写原有 JSON 和图片目录）；JSON 导入自动建立主子题关系和图片映射，ZIP 需另补图。“截图补充上传与关联”“查询题目”默认折叠 | 共 1,279 QA；四维题数为 179 / 61 / 757 / 282；240 个截图帧，全部 QA 关联真实截图，缺图清单为零 |
| **02 参赛名单** | 下载 JSON 示例，或使用 [仓库模板](examples/participant-submission.json)；一次选中多队 JSON，点击“导入参赛配置”；名单每队一行，在下拉框中选版本或“不参赛” | 队伍、模型、凭据状态、聚合声明、版本正确；可搜索队伍、“全部选最新版本”或“清空名单”，实际名单以保存结果为准 |
| **03 设置并启动** | 填写比赛名称，统一选择策略、每题最大调用次数及适用的 Self-refine 提前结束选项；右侧概览实时显示队伍数及最大请求数；点击“开始正式测评” | 配置校验后，确认窗口展示名称、各队选中版本、每队 1,279 QA、策略、次数、最大请求数、截图和模型状态，以及真实 API 费用提示 |
| **04 监控与结果** | 运行时查看指标卡（整体进度、预计剩余、已答题平均准确率、请求与错误、已用时间）、各队分维度准确率和准确率曲线；完成后查看前三名、综合排名与四维热力表、雷达及效率图，导出报告与表格 | “异常与操作”可停止整批或单队、按冻结配置处理可重跑任务；只发布完整完成且无主办方故障的正式成绩，不同执行条件分别比较 |

JSON 导入会直接完成格式校验和整批保存，**不需要再做 Excel/CSV 式的“预览后确认导入”**，也不会调用模型。若其中有无效配置，该次整批不导入；修正后重新提交。Excel/CSV 仍在页面的“兼容导入”折叠区，沿用解析预览后确认的方式。

导入新版本后，系统会更新参赛版本并提示变更；仍须在第二步核对每队实际选中的版本。可手动选择旧版本，界面会提示存在更新版本。名单中不展示 Mock 或不可用的候选方案；正式批次的后端也会拒绝 Mock、局部题目范围或缺少真实截图的配置。

### 确认启动及监控

在最终确认弹窗中逐项核对**队伍名称/编号、选中的版本、模型 ID、聚合代理声明、Prompt 版本与凭据来源**。存在未选中的更新版本时显示黄色警告。JSON 与 Excel/CSV 两种导入都会自动选中新导入的方案版本；选择结果保存到 SQLite，换浏览器不会丢失，也可以点击“全部选最新版本”。格式与凭据状态校验不等于已验证 API 连通性；未提供最近连通性检查结果时，确认窗口不显示该列。

点击 **“确认并开始测评”** 后，平台自动冻结全部配置、创建 Batch 和各队 Run、进入既有队列，并直接展示本批监控，不需要到列表里再找一次启动按钮。取消确认不会创建或启动任务。

最大可见请求数为 `选中队伍数 × 1,279 × 每题允许次数`，Single-pass 固定按 1 次计算。Self-refine / Majority-vote 可选 1～主办方上限；提前结束时实际请求可能更少。所选次数是上限，不是保证每题一定使用的次数。正式入口不提供题数、维度或题目 ID 筛选。

### 并发与限流

- **队间并行**：同一批次的全部队伍同时开始，不再一队接一队，避免后排队伍等待几十小时。
- **队内并发**：设置页“队内并发”选 1 / 2 / 4（默认）/ 8 / 16 套，表示每队同时做几套题（一套 = 一张图配一个主问题和若干子问题）。**并行只发生在不同套题之间，同一套内部不并行**：按“子问题（题库顺序）→ 主问题”依次做；同一道题的多轮（Self-refine）仍按顺序。**全队使用同一个值**以保证公平，并写入冻结的批次配置和启动确认窗口。本机另有全局上限（默认 64 路，环境变量 `WARGAME_GLOBAL_CONCURRENCY` 可调）。
- **并发检测（可选）**：点击“检测各队可用并发”，对每队用真实接口和不同套题的主问题（各带自己的截图），按 1、2、4、8、16 路逐级发送（每队最多 31 次请求，遇到限流或失败即停止，会产生少量费用）。页面给出各队稳定并发和全队统一的建议值，可一键采用；比赛进行中不能检测（`POST /api/competition/probe-concurrency`）。
- **429 限流**：服务商返回 HTTP 429 时，平台在同一个调用名额内等待并重发（等待 1、2、4、8、16、30、30、30 秒，或按 `Retry-After`，最多 60 秒），等待不计入该题的答题时间，也不多占调用次数；仍无法恢复时才按普通接口错误计错。其他错误（超时、5xx、无效输出）仍按原规则计错，不重试。调用记录中的 `rate_limit_retries` 可查看重试次数。
- 停止、故障和进程中断规则不变：停止时各路在当前请求结束后停止，未完成的题不记录；进程中断时运行中的队伍标为中断，不自动重复发送收费请求。

监控区仅对**当前选中的运行批次**每 3 秒刷新各队进度、请求数、错误和耗时；**监控中的准确率 ＝ 已答对 ÷ 已答题数**（不是全部 1,279 题），并标注“暂估”，各维度同时显示已答题数；“准确率随已答题数变化”曲线每约 15 秒更新（`GET /api/evaluation-batches/{id}/accuracy-curves`）。最终成绩、排名和导出仍按全部题目计算，规则不变。历史批次列表每约 15 秒刷新一次，正式页面的流程状态每 10 秒更新。异常队伍优先展示，错误列区分接口错误、超时、无效输出和平台故障。完成至少 20 题后按已完成题目的平均耗时估算剩余时间，估算不改变执行计划。可安全停止整批或单队；当前版本没有暂停后续跑入口。模型 API 错误、普通超时和无效答案默认计错；主办方截图资源等故障按下方“停止、故障与复现”流程登记和处理，不能挑选部分题重测或择优成绩。

如果网络中断、响应丢失或界面提示启动结果尚未确认，使用 **“重试 / 查看本批次启动结果”** 沿用原幂等键核对，不另建一个同名批次来代替重试。进程重启后被标为中断的任务不会自动重放可能收费的请求，应由主办方统一核实后按冻结配置处理。

### 结果发布

“04 监控与结果”顶部的 **自选评测对比** 可选择 2–8 个已完成且可用的记录，覆盖不同批次和独立评测。列表支持按名称、模型、版本、日期或 ID 搜索，展示北京时间、综合分与版本以区分同名结果。首次默认选择最近 3 条可用记录；之后保存并恢复选择，失效记录会清理，不自动混入新记录。“全选可见”超过 8 项时拒绝更改并提示缩小范围。点击“生成对比”显示全部所选记录的四维雷达图（固定 0–100%）、综合分排行和明细，颜色一致，同分并列，两张图均可导出 SVG / PNG。修改选择或刷新列表会清除旧图，需重新生成。页面会展示数据或规则不一致等后端提示；对比不调用模型，也不改变正式排名。原批次监控和报告仍在下方。

在第四步选择正确批次、队伍及 Top N，导出综合 HTML、CSV/XLSX/JSON 和 SVG/PNG 图表。公共报告不包含密钥、Prompt 正文、GT 或逐题模型输出。历史单任务报告与排行榜在该页的 **“历史报告与单次测评排行榜”** 折叠区；历史测试只作联调参考，不进入正式榜。归档本轮批次、版本、冻结规则和正式报告，按主办方安排发布结果。

## 补充操作：数据处理与开发者调试

以下为底层操作入口说明；**正式比赛以以上四步流程为准**。开发者单任务入口用于联调，界面提交 `official=false`，支持 Mock 和局部题目，成绩不进入正式榜。

1. **数据集管理**：优先使用“工作区一键导入”；题库和截图不在项目目录时，可用“本地路径导入”直接读取原有路径，或用“手动选择文件”（选 `qa_all.json` 与截图文件夹，接口 `POST /api/dataset/import-upload`，校验规则与工作区一键导入相同，截图文件夹内非图片文件会被忽略）。具体格式见下节。相同内容重复导入不会重复计数；工作区及手动上传更新已有题库时自动备份，页面显示输入文字变化数量（包括换行差异）。兼容导入页签仍可导入工作区 ZIP 或上传 ZIP；本地路径与 ZIP 导入在题库不同时拒绝覆盖。按 ID、复盘、层级、主题/子题查询，查看原始输入和仅管理员可见的 GT / 标注。
2. **截图关联**：一键导入已完成自动关联。需要手动补充时可下载缺图清单，上传 PNG/JPEG/WebP，声明是真实截图还是 Mock，再填写复盘 ID 与数据 step。相同复盘与 step 下全部 QA 共用一个图片；文件按 SHA-256 去重。仍可粘贴 JSON 清单批量映射。运行中冻结图片哈希，文件被篡改或丢失会标记主办方资源故障。
3. **模型配置**：选择 OpenAI-compatible，填写公网 HTTPS Base URL（通常含 `/v1`）、Model ID、API Key 或环境变量名，并明确声明是否为聚合代理。支持新增、编辑、删除和连接测试；真实服务的连接测试仅发起一次短请求，仍可能产生少量费用。
4. **Prompt 与推理**：主办方录入选手提交的 System / Initial / Review，保存新版本；不要用主办方自行设计的内容替换选手 Prompt。页面上的默认模式、次数、提前结束选项是主办方设置的执行默认值，不属于选手三段 Prompt 正文。保存的版本不可覆盖，旧任务始终使用原版本；在创建任务页选择版本会加载这些默认值。
5. **创建任务**：主办方选择模型、选手 Prompt 版本、三种推理模式之一及题目范围，确认次数和提前结束规则。实际执行以该任务的冻结配置为准。可指定维度、ID 列表、最多题数或全量；留空题数即全量。任务在后台执行。没有真实截图时使用内置 Mock 图像和 Mock API 联调，真实模型测试也要求所选题目全部有真实截图。
6. **任务监控与报告**：自动刷新进度、错误数、答错数、耗时及调用统计。查看每题答案、各轮输出、用量、耗时及错误；导出 JSON / CSV / HTML。正式全量、Mock、真实模型测试分区展示，按同一冻结规则组排名；排行榜显示题数，防止把不同范围测试误认为同一全量比赛。

### 从 qa_all.json 一键导入

目录放在**服务所在机器的项目根目录**，浏览器不需要逐个选择文件：

```text
wargame-eval/
  images/
    qa_all.json
    G01-01_G01-01_step0_<UUID>.png
    G01-02_G01-02_step2710_<UUID>.png
    ...
```

打开 **正式比赛 → 01 数据集**，选择 **“工作区一键导入”** 并点击 **“一键导入工作区题库与截图”**（页面会先显示 `qa_all.json` 与截图是否找到）。此按钮向 `POST /api/dataset/import-local` 发送无请求体的请求，只读取固定的本地 `images/` 目录，不调用模型 API。主办方需确认该目录内的截图为真实比赛截图，导入后图片按真实来源登记。

**保留本地路径导入**：数据已经存放在 G 盘等其他目录时，选择第 4 个页签“本地路径导入”，填写 `qa_all.json` 和截图文件夹的完整路径，点击“一键导入 QA 与截图”。首次进入数据集页会通过 `GET /api/dataset/local-source` 加载既有路径；两条路径齐全时默认显示该页签，之后保留管理员手动选择的导入方式和填写内容。该入口使用同一个 `POST /api/dataset/import-local`，但带 JSON 请求体 `{"qa_path":"完整 JSON 路径","images_dir":"完整截图目录"}`；直接读取服务所在电脑上的文件，无需复制或浏览器上传。它保留原本地导入的严格规则：完整校验后写入，相同数据重复导入安全，**不同题库拒绝覆盖**。导入成功后自动刷新题库、截图与比赛就绪状态；运行或排队期间的限制仍适用。Docker 中需填写容器可访问的挂载路径。

`qa_all.json` 顶层为题目数组，字段按以下方式读取：

| JSON 字段 | 用途 |
|---|---|
| `id`、`sample_id`、`role` | 唯一题目 ID；同一 `sample_id` 必须有且只有一个 `core` 主问题，其余 `subquestion` 自动关联到它 |
| `replay.id`、`replay.step` | 实际图片映射键；同组主子题的复盘、step 和图片路径必须一致 |
| `image.path` | 优先读取该路径（相对根目录 `images/`）；如旧路径不存在，匹配平铺截图名 `<sample_id>_<sample_id>_step<step>_<UUID>.png`，也支持 JPG/JPEG/WebP 扩展名 |
| `model_input`、`source.model_input_sha256` | 完整模型输入及其 SHA-256；逐字符保留，包括末尾换行，校验不符拒绝导入 |
| `options`、`answer.labels`、`type`、`level` | 原始选项、GT、单选/多选类型及评测层级；验证选项与输入、答案一致 |
| `review_markdown`、`source` | 管理员参考标注及来源记录；不会加入发给模型的公开输入 |

先验证全部题目和图片，再在同一数据库事务中写入题库与关联。重复 ID、缺少主问题、四维数量不符、找不到图片、图片匹配不唯一或图片无效时整批拒绝。`qa_all.json` 最大 20MB；单张图片最大 20MB、4000 万像素；整批图片最大 500MB。已有 Mock 来源的相同图片不能改成真实来源。

通过工作区或手动上传更新当前题库或映射前，自动将旧题库和旧映射备份到 `data/raw/dataset-backup-<ID>.json`；原始新 JSON 也按哈希存档。旧图片资源继续保留，已有任务、成绩和冻结快照不改写；新任务按新题库生成快照和规则组。运行、排队或停止中的任务会阻止导入，需结束后再操作。相同题库与映射再次导入不会创建重复 QA 或重复备份。本地路径及 ZIP 入口继续拒绝覆盖不同题库。

Docker 用户可额外将主机 `./images` **只读挂载**到容器 `/opt/wargame/images` 后使用该按钮；私有数据不进入构建镜像。原始 ZIP 与手动上传/关联方式继续可用。

截图批量映射示例（手动补图时，先通过上传取得 `image_id`）：

```json
[
  {
    "replay_id": "20220203110412901-211520121-AVJ4qyTl",
    "image_step": 0,
    "image_id": "上传返回的 SHA-256"
  }
]
```

服务无法自动判断上传图像是否为真实兵棋截图，也不审核截图语义；真实性声明和复盘/step 映射由管理员负责。内置 Mock 图片有明确文字标识，且不能将已存储的 Mock 图片直接改为真实图片。

## 执行规则

默认配置在 `config/settings.yaml`，也能在界面“主办方执行规则”保存：

```yaml
competition:
  max_calls_per_question: 3
  timeout_per_question_seconds: 120
```

每次创建任务读取最新配置，执行时使用冻结快照。修改上限无需修改源码；已有任务不会被中途改变规则。任务实际次数由主办方按赛规确认，若接收选手申报也必须在 1～主办方上限之间，越界拒绝，不会静默扩大预算。

- **Single-pass**：固定一次请求，推理次数字段不增加调用。
- **Self-refine**：当前题内追加上一轮回答及 Review Prompt，最多所选次数；可在连续两次合法答案集合相同时提前结束。最终轮非法输出计错，不回退挑选较早答案。
- **Majority-vote**：各次从完全相同的初始消息独立采样，不共享输出。仅合法答案参与投票；并列选出现最早的合法并列答案；没有合法答案则计错。不发起额外裁决请求。
- HTTP 客户端无自动重试、不跟随跳转、不使用系统代理。每次尝试在发送前持久化占用一个预算槽，HTTP 错误、连接失败、超时同样消耗预算。连接在发送前即失败也保守计入，避免故障重试形成预算漏洞。
- 每题共享一个总截止时间，而非每轮重置 120 秒；普通超时计错，即使前轮已有合法采样。Token Usage 仅在 API 返回时统计，没有返回时不会估算成真实用量。
- 每题重新构造消息，只给模型完整原始输入、截图及用户 Prompt；GT、参考推理、父题答案、其他题目历史均不进入模型消息。Mock HTTP endpoint 也不读取 GT 或数据库。

## 评分与正式榜准入

数据维度：L2 主题 **179**、L3 主题 **61**、L1 子题 **757**、L2 子题 **282**；240 个唯一截图帧。输入块原样保留，标准化 JSONL 位于 `data/processed/questions.jsonl`（含 GT，仅管理员使用，不直接发送给模型）。原始 ZIP 另按哈希留存在 `data/raw/`。

单选严格匹配，多选集合完全匹配；兼容纯字母、`A、C、D`、`ACD`、JSON `{"answer":"C"}` / `{"answer":["A","C","D"]}` 和 JSON 代码围栏。含解释性散文而没有明确结构的输出不会猜测提取。重复字母、越界选项、弃答及无效输出计错。

```text
综合分 = 100 × (0.35 × L2主题准确率 + 0.35 × L3主题准确率
              + 0.15 × L1子题准确率 + 0.15 × L2子题准确率)
```

四维均为普通准确率，没有 L3 平衡准确率，也不使用 LLM 评分。局部测试缺失维度显示“—”，在加权计算中按零贡献处理，不重分配权重；未完成题目不计为正确，任务完成前分数为暂态；监控页另显示仅按已答题数计算的“当前准确率”（API 字段 `answered_accuracy`，仅供观察）。图表统一使用一套队伍配色，雷达图坐标按数据范围缩放并在图上标注中心值。

正式批次固定为正式比赛，创建要求：精确全量四维数量、所有题目关联真实截图、真实模型服务。正式榜额外要求任务完整完成、没有主办方基础设施故障。规则组指纹覆盖数据、截图、主办方预算、超时、权重。V1.2 排名额外区分批次、模式、实际次数与提前结束开关；这些执行条件不同的任务分别排名。批次内每队只绑定一个方案及当前有效运行，基础设施重跑替换当前绑定并保留历史，不自动取最高分。

Mock 无论跑 5 题还是 1279 题均为 **联调结果，不是实际 Benchmark**。聚合代理内部模型调用无法完全观测；预算仅约束平台可见 HTTP 请求，依赖选手声明。

## 停止、故障与复现

任务、冻结数据/截图/模型/Prompt/规则快照、结果及逐次调用均存入 `data/wargame.sqlite`。

- 浏览器刷新不丢失任务。
- 安全停止等待当前请求完成或超时，然后停止后续请求，已花费的调用不恢复预算。
- 服务进程退出或崩溃后，未完成任务标为 `interrupted`，不会自动重发可能已收费的请求。优雅退出也保存此状态。
- 本地截图缺失/哈希不符等故障标为 `infrastructure_error`；API 连接异常、HTTP 错误、普通超时属于模型请求错误，默认计错。
- 管理员可在报告底部登记已证实的主办方故障、受影响题目和原因。原结果、原因、登记时间及原调用记录保留，成绩不进入正式榜。
- 只有基础设施故障/进程中断可使用“按冻结配置重跑”。它创建新的 `run_id`，全量重新执行原冻结范围，旧 run 标记 `superseded` 排除出榜；新任务记录 `replaces_run_id`。主办方应对同一故障影响到的参赛配置统一重跑，不择优挑选部分题结果。重跑可能重新产生模型费用，启动前请核实费用及比赛安排。

## 凭据与部署边界

优先在进程环境中设置服务密钥，在模型配置中填写变量名，例如 `MODEL_API_KEY`。也可在页面输入 Key，使用 Fernet 加密后保存；首次使用自动生成 `data/.secret.key`。可通过 `WARGAME_SECRET_KEY` 提供持久 Fernet 主密钥。**请同时备份数据库、图片、配置与主密钥**，并限制数据目录的 Windows ACL / 文件权限；原型不接入企业 KMS，数据库文件和本地主密钥被同时读取会失去加密保护。

为冻结复现，环境变量中的 API Key 在创建任务时解析为加密快照。API Key 不在 API 响应、日志、报告或排行榜回显；模型输出中的当前 Key 会被替换，API 异常仅记录安全类型和错误码分类。不要把其他密钥手动写入 Prompt 或队伍名称。

自定义 API 只允许公网 HTTPS，端口 443/8443，禁止 URL 内嵌凭据、查询串和 fragment。保存时校验 DNS，建立连接时重新校验全部解析结果并直接连接已检查的公网 IP，TLS 仍使用原域名校验证书，阻止 DNS 重绑定；禁止私网、环回、链路本地、保留地址及常见 IPv6 隧道地址。不允许跳转、不继承系统代理；这会阻止公司内网 API、localhost 模型和强制代理环境，后续应由主办方增加受控适配器，而非关闭保护。

此版本是**单管理员本地原型**，没有参赛者身份、租户隔离、公开管理接口鉴权、分布式队列或生产级审计。`start.py` 仅绑定本机，并启用 Host / Origin 检查与 CSP。排行榜接口/导出不含 Prompt 和 API 凭据，但管理员接口可读取 GT，**不能把整个服务直接公开到互联网**。后续公开部署需要管理员鉴权、权限隔离和独立公共榜服务。Docker 亦仅映射本机端口。
