# 庙算杯态势感知赛道参赛须知

适用平台：Wargame-Eval V1.3。本文面向参赛选手，说明需要提交的材料、模型接口要求及测评方式。提交渠道、截止时间、评测窗口、联系人，以及本轮采用的推理策略、调用次数和超时，由主办方另行公布；本文不代替这些具体安排。

## 1. 参赛方式与双方分工

本赛道通过模型 API 进行多模态问答测评。**选手提供可访问的模型服务，自行设计三段 Prompt，并提交一份 JSON 配置；主办方操作后台、导入方案并统一执行正式比赛。** 选手无需操作管理后台，也无需为平台编写 Agent 程序。

- 模型来源开放，不限制模型参数量。服务须符合本文的接口和网络要求。
- 允许模型聚合代理，必须通过 `is_aggregator` 如实申报。平台只统计可见的模型 API 请求，无法观测代理内部的模型调用。
- 主办方保管正式 QA、截图、标准答案和参考标注。模型只收到当前题目的公开输入、对应截图及选手 Prompt，不收到 GT、参考推理或其他题目的回答。
- 正式批次固定全量 1,279 道 QA，仅使用真实模型和真实截图。Mock 与局部测试只用于主办方的开发调试，不进入正式排行榜。

## 2. 需要提交什么

每支队伍每个方案版本提交一份 UTF-8 编码的 `.json` 文件，建议命名为 `队伍编号_版本.json`，例如 `team-001_v1.json`。

下载并填写 [参赛配置模板](../examples/participant-submission.json)。模板中的地址、模型名称和 Prompt 是示例，`api_key` 留空，**须替换为本队实际配置后，才能用于正式导入**。

| 字段 | 填写要求 |
|---|---|
| `team_id` | 主办方确认的稳定队伍编号，1～80 个字符；建议使用字母、数字和短横线 |
| `team_name` | 队伍名称，1～80 个字符；同一 `team_id` 各版本须使用相同名称 |
| `submission_version` | 方案版本，1～80 个字符，例如 `v1`、`v2` |
| `api.base_url` | 模型服务 Base URL，通常以 `/v1` 结尾，不能填写完整的 `/chat/completions` 地址 |
| `api.model_id` | 服务实际支持的模型名称，1～80 个字符 |
| `api.provider` | 正式参赛填写 `openai`，表示 OpenAI-compatible 接口，不限定服务商 |
| `api.is_aggregator` | 是否为模型聚合代理，必须明确填写 JSON 布尔值 `true` 或 `false` |
| `api.api_key` | 有效访问凭据；通过主办方约定的安全渠道提交 |
| `prompts.system` | 选手设计的 System Prompt，非空，每段最多 20,000 个字符 |
| `prompts.initial` | 选手设计的 Initial Prompt，非空，每段最多 20,000 个字符 |
| `prompts.review` | 选手设计的 Review Prompt，非空，每段最多 20,000 个字符 |
| `inference.temperature` | 温度，范围 0～2；模板值为 0 |
| `inference.max_tokens` | 单次响应的最大输出 Token 数，整数 1～16,384；模板值为 1,024 |

若主办方要求使用环境变量交付凭据，可将 `api.api_key` 留空，另填 `api.api_key_env`，例如 `TEAM_001_API_KEY`。该名称指**主办方运行服务的环境变量**，不是选手电脑上的变量；须事先与主办方完成密钥配置。`api_key` 与 `api_key_env` 只能填写一个。

主办方可一次导入多份 JSON，单次最多 100 个文件、100 份方案，文件总大小不超过 8,000,000 字节。推荐每队一份文件，避免多人合并时修改其他队伍的配置。平台也兼容 Excel/CSV，由主办方按收集安排决定是否使用。

## 3. 三段 Prompt 如何设计

三段 Prompt 均由选手设计并提交，不能用主办方编写的统一 Prompt 替代选手方案。**正式提交必须三段齐全**；某段本轮未被使用时仍会保存归档。

| 部分 | 作用 | 何时使用 |
|---|---|---|
| **System** | 定义模型角色、总体判断原则、信息边界与输出约束 | 三种推理策略都使用；Self-refine 后续轮次保留 |
| **Initial** | 指导首次解题，例如核对单位、位置、阵营、旗标及选项 | Single-pass 的唯一调用、Self-refine 的首轮、Majority-vote 的每次独立采样 |
| **Review** | 指导模型复核当前题的上一轮回答，发现遗漏或矛盾后修正 | 仅 Self-refine 的第二次及后续调用 |

三段不是三个固定调用次数，也不是三道题。完整题干、背景、选项和截图由平台自动附加，不需要将 QA 粘贴进 Prompt；当前平台不替换 `{question}`、`{image}` 等占位符。

建议 Prompt 要求模型遵循题目的单选/多选要求，最终返回明确的选项字母或结构化答案。具体 Prompt 内容由各队自行设计。更详细的调用关系和写法说明见 [三段 Prompt 说明](prompt-submission.md)。

## 4. 模型 API 必须满足的要求

平台当前使用 **OpenAI-compatible Chat Completions** 协议，实际请求地址为：

```text
POST {api.base_url}/chat/completions
Authorization: Bearer <API Key>
```

例如 Base URL 填写 `https://api.example.com/v1`，平台会请求 `https://api.example.com/v1/chat/completions`。请勿重复填写末尾的接口路径。

服务需接收 `model`、`messages`、`temperature`、`max_tokens`。`messages` 可能包含 `system` 消息，以及同时包含 `text` 和 `image_url` 的用户消息；图片通过 `data:image/...;base64,...` 形式发送。Self-refine 还会发送同一道题的历史回答与复核指令。

返回应为非流式 JSON，模型输出位于 `choices[0].message.content`，且该字段必须是字符串。例如单选答案 A 的返回结构为：

```json
{
  "choices": [
    {"message": {"role": "assistant", "content": "{\"answer\":\"A\"}"}}
  ]
}
```

可以返回 `usage` 中的 Token 用量；未提供时平台不估算真实用量。仅返回 `{"answer":"A"}` 作为整个 HTTP 响应，或只返回流式事件、工具调用而没有字符串正文，都不符合当前接口要求。

网络要求：服务必须可从主办方运行环境通过**公网 HTTPS、端口 443 或 8443**访问，使用有效 TLS 证书。Base URL 不得内嵌账号密码、查询参数或片段；不支持 localhost、私网地址、HTTP 跳转或必须依赖系统代理才能访问的服务。如服务有来源 IP 白名单，应提前与主办方联调。

请确保评测窗口内服务持续在线、凭据有效，并具备足够配额。平台按队伍顺序执行，不保证各队在同一时刻开始；具体窗口由主办方通知。

## 5. 推理策略与调用预算

**推理策略、每题调用次数、总超时和提前结束规则由主办方统一设置，选手不能通过 JSON 或 Prompt 改写平台执行规则。** `temperature`、`max_tokens` 不代表调用次数。

| 策略 | 调用方式 | 最终答案 |
|---|---|---|
| Single-pass | 每题固定 1 次 | 本次输出 |
| Self-refine | 首轮解答后，在当前题上下文中按 Review 检查修正，最多所选 N 次，包含首轮 | 最后一次输出；最后一轮无效时不回退挑选较早答案 |
| Majority-vote | 对同题执行最多所选 N 次独立采样，各采样不共享输出 | 平台对合法答案投票；并列时取最早出现的合法并列答案，不额外调用模型裁决 |

当前默认主办方上限为**每题 3 次模型 API 请求**、**每题共享 120 秒总超时**。这些是可配置的默认值，本轮实际采用的策略、次数及超时以主办方公布并冻结的规则为准，不保证一定使用 3 次。Self-refine 若启用连续合法答案相同提前结束，实际调用可能少于上限。

HTTP 错误、连接失败和超时也占用预算，平台不做额外自动重试。总超时覆盖当前题的全部轮次，不会每轮重新获得完整超时。API 错误、普通超时或无效答案默认计错；主办方资源故障按故障流程单独处理。

每队全量比赛的可见 API 请求上限为 `1,279 × 每题实际允许次数`；Single-pass 为 1,279 次，允许 3 次的多轮策略上限为 3,837 次。聚合代理内部请求不在平台可见统计内，仍须如实申报代理身份。

## 6. 评分与正式成绩

每队完整评测 1,279 道 QA，四维均采用普通准确率：

| 维度 | 题数 | 综合分权重 |
|---|---:|---:|
| L2 主问题（`L2_main`） | 179 | 35% |
| L3 主问题（`L3_main`） | 61 | 35% |
| L1 子问题（`L1_sub`） | 757 | 15% |
| L2 子问题（`L2_sub`） | 282 | 15% |
| 合计 | 1,279 | 100% |

综合分满分 100：`100 × (0.35 × L2主准确率 + 0.35 × L3主准确率 + 0.15 × L1子准确率 + 0.15 × L2子准确率)`。

- 单选须与标准答案一致；多选须选项集合完全一致，漏选、多选均计错，不按部分正确给分。
- 支持明确的字母答案，如 `A`、`ACD`、`A、C、D`，以及模型正文中的 `{"answer":"A"}` 或 `{"answer":["A","C","D"]}`。推荐使用 JSON 答案，避免混入无法解析的解释性文字。
- 重复字母、越界选项、弃答、无效输出及普通 API 请求错误计错，不使用另一个大模型主观打分。
- 未完成任务和存在主办方基础设施故障的任务不进入最终正式排名。Mock、历史测试和局部调试成绩不进入正式榜。
- 不同批次或不同冻结执行条件分别比较。同一队伍每个批次只使用一个方案版本，不从历史运行中挑选最高分。

结果由主办方统一发布。平台支持综合排名、四维准确率、雷达图、效率分析以及 CSV/XLSX/HTML 等导出；公共报告不包含 API Key、Prompt 正文、GT 或逐题模型输出。

## 7. 版本更新与凭据交付

同一 `team_id + submission_version` 的完全相同配置会被视为重复提交；内容改变时必须使用新版本号，不能覆盖原版本。变更模型地址、模型名称、凭据、Prompt 或推理参数后，请提交新版本并通知主办方核对。

正式启动前，主办方冻结本批的队伍版本、三段 Prompt、模型凭据、题库、截图和执行规则。测评开始后不要擅自使原服务或凭据失效；如需更换或发生故障，应及时联系主办方，由其按赛程决定处理方式。主办方基础设施故障重跑保留原记录，不以挑选部分题目或择优成绩替代全量结果。

包含真实 API Key 的 JSON **只通过主办方约定的安全渠道交付**，不要提交到 GitHub、Issue、公开网盘或公共聊天群。公开仓库中的配置模板不包含真实凭据。建议提供仅用于本次测评的访问凭据，交付后的有效期、配额及失效安排与主办方确认。

## 8. 提交前核对

- 已从模板填写队伍编号、名称、方案版本，且与主办方登记一致。
- 正式服务为真实多模态模型，支持上述消息格式、图片输入、Bearer 认证及非流式返回。
- Base URL 为可访问的公网 HTTPS 地址，Model ID 正确，凭据有效，白名单与配额已确认。
- `is_aggregator` 已如实填写；三段 Prompt 均由本队设计，非空且未超过长度上限。
- JSON 使用 UTF-8，字符串换行写为 `\n`，内部双引号正确转义，无注释、尾随逗号或真实密钥的公开副本。
- 已按主办方通知的截止时间和安全渠道提交，并确认本轮采用的推理策略、次数和超时。
