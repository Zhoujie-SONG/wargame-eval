# 选手 Prompt 提交与主办方执行说明

完整交付材料与比赛规则见 [《庙算杯态势感知赛道参赛须知》](participant-guide.md)，可填写的文件见 [JSON 参赛配置模板](../examples/participant-submission.json)。本文解释三段 Prompt 的含义与调用关系。

本平台由主办方统一操作。选手负责模型服务和 Prompt 设计，不需要编写 Agent，也不需要进入管理后台。**选手提交三段 Prompt，主办方选择推理模式并统一执行测评。**

## 一、双方分工

| 工作内容 | 负责方 |
|---|---|
| 提供模型 API 地址、Model ID、可用凭据及聚合代理声明 | 选手 |
| 设计并提交 System、Initial、Review 三段 Prompt | 选手 |
| 保管正式 QA、真实截图、GT 和参考推理 | 主办方 |
| 在管理界面录入选手配置、保存 Prompt 版本 | 主办方 |
| 选择本轮推理模式、确定实际调用次数和提前结束规则 | 主办方按赛规执行 |
| 设置每题调用上限、总超时及全量正式批次；选择开发调试范围 | 主办方 |
| 创建任务、冻结配置、监控、评分及发布结果 | 主办方 |

Prompt 的设计者是选手，后台录入者是主办方。这两种角色不能混淆。主办方应保留选手提交原文；如需修订，应由选手提交新版本，并在正式测评前重新确认和冻结。

## 二、三段 Prompt 分别写什么

### 1. System Prompt：总体角色与作答原则

字段名：`system`。

用于指定模型的角色、总体分析原则、可以使用的信息和作答约束。它不包含具体试题，而是可复用于不同题目的总体指令。

可包含：

- 模型应承担的分析角色。
- 只依据给定截图和背景作答，不补充未提供的战场信息。
- 区分当前可见事实、历史记录与尚未发生的行动。
- 遵循原题的单选、多选及输出格式要求。

示例（仅说明写法，由选手自行设计最终内容）：

```text
你是一名兵棋态势分析助手。请仅根据当前题目提供的静态截图和文字背景判断。
区分当前可见事实、历史记录与未来计划，不补充未提供的战场信息。
遵循原题的单选或多选要求及输出格式。
```

平台将非空 System Prompt 作为 `system` 消息发送。Single-pass、Self-refine 和 Majority-vote 都使用这一段；Self-refine 后续轮次会继续保留它。

### 2. Initial Prompt：第一次如何解答

字段名：`initial`。

用于指导模型面对当前题目时应怎样处理输入，例如先核对哪些图像要素、怎样结合背景、如何在选项之间作出判断。

可包含：

- 关注单位 ID、阵营、位置、血量及据点旗标等要素。
- 将图像证据与题目明确提供的背景对应。
- 对照全部选项，并按原题要求返回最终选项。

示例：

```text
请独立解答本题。先核对截图中相关单位的阵营、ID、位置和据点旗标，
再结合题目提供的背景比较各选项，按原题要求输出最终选项。
```

平台把 Initial Prompt 放在首次 `user` 消息的原始题目前，并同时附上完整题干、背景、选项和截图。选手不需要在 Prompt 中复制原始 QA，也不需要填写 `{question}`、`{image}` 等占位符；当前系统不对这些占位符做模板替换。

生效方式：

- Single-pass：唯一一次调用使用它。
- Self-refine：首轮调用使用它，后续轮次保留首轮上下文并追加 Review。
- Majority-vote：每次独立采样都使用相同的 Initial Prompt 和原始题目。

### 3. Review Prompt：如何检查和修正

字段名：`review`。

用于在 Self-refine 后续轮次要求模型检查当前题前面的回答，核对依据并给出修正后的最终答案。它应是一段通用检查指令，不需要预先知道试题或模型会回答什么。

可包含：

- 回看截图，检查是否看错位置、阵营或旗标。
- 检查是否把历史计划当成当前状态，或引入了未提供的事实。
- 多选时检查是否漏选或多选。
- 有误则修正，无误则保留，并再次明确输出最终答案。

示例：

```text
请复核你对当前题的上一轮回答，并重新核对原始截图和背景。
重点检查单位位置、阵营、据点归属，以及是否把历史计划当成当前事实。
若有错误，请修正；若无错误，请保留。按原题要求输出最终选项。
```

平台会在当前题的消息历史后追加上一轮模型回答，再以新的 `user` 消息发送 Review Prompt。模型能看到当前题已有的上下文，不会得到其他题的回答、GT 或参考推理。

**Review 只在 Self-refine 的第二次及之后调用时发送。Single-pass 和 Majority-vote 不发送 Review。** 即使选中 Self-refine，如果实际只允许调用一次，也不会进入 Review 环节。

## 三、正式提交格式

V1.4 正式收集使用一队一份 UTF-8 JSON，完整填写队伍、模型 API、凭据或环境变量引用、聚合声明、三段 Prompt 及支持的模型参数。请填写 [JSON 模板](../examples/participant-submission.json)，字段、接口和交付要求以 [参赛须知](participant-guide.md) 为准；主办方可一次导入多队文件。

**正式导入必须同时提交全部三段非空 Prompt，每段最多 20,000 个字符。** 未被本轮模式使用的段落只保存，不发送。例如 Single-pass 的 Review 会归档，但不会进入请求。这与选手必须交齐三段材料并不矛盾。

API 凭据通过主办方指定的安全渠道交付，不能写进 Prompt、公开仓库或公共报告。模板中的 `api_key` 为空，填写真实配置后方可用于正式导入；若使用 `api_key_env`，须由主办方在实际运行服务的环境中预先配置。

JSON 和兼容的 Excel/CSV 入口均强制三段非空并保留内容。开发者单配置编辑为兼容旧任务仍允许 System / Initial 留空，Self-refine 的 Review 留空时使用程序内置通用检查指令；这些兼容行为不能代替正式参赛材料。

## 四、推理模式由主办方选择

选手提交的三段 Prompt 是作答指令，推理模式是主办方控制的执行流程，两者分别管理。主办方应在正式测评前说明本轮或本赛道采用的模式，让选手能针对已公布的流程设计 Prompt。

| 主办方选择的模式 | 平台怎样调用 | 使用的选手 Prompt | 最终答案 |
|---|---|---|---|
| Single-pass | 一次独立调用 | System + Initial | 此次回答 |
| Self-refine | 首轮作答，后续在同题上下文中检查修正 | 首轮 System + Initial；后续保留上下文并追加 Review | 最后一轮回答 |
| Majority-vote | 多次独立调用，同题各采样不共享生成结果 | 每次相同的 System + Initial | 平台按合法答案投票 |

无论哪种模式，平台都会提供完整原始 QA 和对应截图。Self-refine 最后一次输出非法时按无效输出处理，不自动挑选之前的合法答案；普通超时计错。Majority-vote 平票时选择最先出现的合法并列答案，不额外调用模型裁决。

正式同一轮或同一赛道应使用主办方公布的一致模式与执行规则。如果想同时考察单次能力、复核能力和独立采样投票表现，可以分别安排三轮或三个赛道，并分别标明成绩对应的模式。

V1.2 批次由主办方统一选择模式、次数和提前结束规则；排行榜在数据/截图规则组之外进一步按这些执行条件分组。不同批次不混排，未完成或主办方故障任务不进入最终排名。同一队伍每个批次只选一个方案版本，不从历史运行中择最高分。

## 五、主办方在界面中的操作

官方测评人员按 [README 的正式测评操作说明](../README.md#主办方正式测评操作) 执行：

1. 在“01 数据集”准备完整 1,279 QA 及对应真实截图。
2. 在“02 参赛名单”导入选手 JSON，核对模型、三段 Prompt 的方案版本及凭据状态，用下拉框选择每队本轮唯一版本。
3. 在“03 设置并启动”统一设置策略、次数及提前结束规则，点击“开始正式测评”，核对规模和费用后确认。系统自动冻结、创建并启动整批。
4. 在监控区跟踪执行，在“04 监控与结果”核对、导出及发布正式成绩。

“开发者选项”中的模型、Prompt 编辑和单任务测评用于联调。Prompt 页的默认模式、次数和提前结束选项是开发者单任务的执行默认值，不属于三段 Prompt 正文；正式批次使用第三步统一选择的规则。

Prompt 由选手设计不表示选手拥有后台权限。管理后台包含 GT、参考推理和凭据管理能力，只由主办方操作。选手更改方案应提交新版本，主办方核对后选择；已启动批次保留原冻结配置。
